# 智能分配作战台设计

## 背景

当前系统已经具备学生管理、学校分发、手动分配、自动均摊、线索治理、操作日志和批次回滚能力。下一阶段的主要问题不是缺少一个分配按钮，而是未分配池规模较大，管理员需要更清楚地知道“今天应该分哪些线索、分给谁、每人多少、为什么这样分”。

本地数据库快照显示：

- 学生总量约 5.7 万。
- 未分配学生约 5.4 万。
- 已有拨号日志约 2400 条，但坐席负载差异明显。
- 重复主手机号组约 800 多组，需要在分配时默认规避高风险重复线索。

因此，本设计在现有线索治理能力之上新增“智能分配作战台”，把分配从一次性人工操作升级为可预览、可解释、可确认、可回滚的运营动作。

## 目标

- 在“线索治理”下新增智能分配入口，避免继续加重学生管理页面。
- 以公平工作量为第一目标，让启用坐席的活跃任务量尽量接近。
- 分配前提供可解释预览，包括分配池统计、坐席负载、建议新增数量和风险提示。
- 管理员确认后才执行分配，不做静默自动分配。
- 执行时写入批次号和操作日志，继续支持现有分配批次回滚。
- 默认排除已报名、无效、已分配和高风险重复手机号线索，降低错误分配成本。

## 非目标

- 不在第一版做每天自动定时分配。
- 不做黑箱转化率模型，也不按“谁最擅长某学校”优先抢高价值线索。
- 不改变现有手动分配、自动均摊、学校分发和批次回滚入口。
- 不在第一版新建独立分配任务表；分配预览实时计算，执行后以学生归属和操作日志为准。
- 不自动清理重复手机号，只在智能分配中默认排除并提示治理。

## 推荐方案

采用“后端统一计算建议 + 前端作战台预览 + 管理员确认执行”的方案。

后端新增两个接口：

```text
GET /api/admin/smart-assign/preview
POST /api/admin/smart-assign/execute
```

预览接口根据筛选条件实时计算可分配线索、坐席负载和建议分配方案。执行接口不信任前端传回的学生列表，而是用同一套筛选参数在服务端重新计算并落库，避免预览过期或前端篡改。

## 备选方案与取舍

### 方案一：智能分配作战台

后端计算建议，前端展示预览，管理员确认执行。

优点：

- 保留管理员确认权。
- 规则集中在后端，便于测试和复用。
- 分配理由可解释，适合当前运营阶段。
- 能直接接入现有批次日志和回滚。

缺点：

- 第一版仍需要管理员手动触发。
- 规则准确性需要随着真实使用逐步校准。

### 方案二：分配池健康度看板

只展示未分配池结构和风险，不给出坐席分配建议。

优点：

- 实现最轻。
- 几乎不改变现有分配流程。

缺点：

- 管理员仍然需要人工判断分给谁。
- 对公平负载的改善有限。

### 方案三：自动日配额

系统每天按规则自动给坐席分配固定数量线索。

优点：

- 自动化程度最高。
- 对大规模未分配池处理速度最快。

缺点：

- 规则不准时容易造成错误分配。
- 自动写入归属风险更高，第一版不适合直接上线。

结论：第一版选择方案一。

## 分配规则

### 线索候选范围

默认只选择满足以下条件的学生：

- `assigned_to is null`
- 状态为未联系或兼容的历史未联系状态。
- 非已报名、非无效。
- 至少有一个监护人电话。
- 不属于高风险重复主手机号组。

管理员可以通过页面参数进一步筛选：

- 学校名称
- 地区
- 本次分配总量
- 单个坐席新增上限

### 线索排序

候选线索按以下优先级排序：

1. 电话信息完整优先。
2. 非重复手机号优先。
3. 新导入或长期未分配优先。
4. 当前学校/地区筛选范围优先。
5. `id` 升序兜底，保证同样条件下结果稳定。

### 坐席负载

只统计启用话务员。每个坐席计算以下指标：

- 当前活跃任务数：未联系、已联系、未接、待回访。
- 今日拨号数。
- 近 7 天处理量。
- 逾期回访数。
- 当前名下未联系数。

第一版采用可解释负载分，不做复杂模型：

```text
负载分 =
  当前活跃任务数 * 1.0
  + 今日拨号数 * 0.3
  + 近 7 天处理量 * 0.2
  + 逾期回访数 * 2.0
```

负载分越低，越优先补充线索。逾期回访作为惩罚项，避免继续给未处理回访较多的坐席加压。

### 公平分配策略

分配过程按公平优先执行：

1. 计算启用坐席当前活跃任务数和平均任务数。
2. 优先给低于平均值的坐席补齐，直到接近团队平均。
3. 如果仍有剩余线索，按负载分从低到高轮询分配。
4. 每个坐席不得超过本次单人新增上限。
5. 如果所有坐席都达到上限，剩余线索继续留在未分配池。

## 页面设计

入口放在“线索治理”下，命名为“智能分配”。

页面分四块：

### 分配池概览

展示：

- 未分配线索总数。
- 当前筛选下可分配线索数。
- 因重复手机号排除数量。
- 因无电话或状态不符合排除数量。
- 学校和地区分布摘要。

### 筛选与参数

管理员可设置：

- 学校筛选。
- 地区筛选。
- 本次分配总量。
- 单个坐席新增上限。

默认值：

- 只分配未分配、未联系线索。
- 分配总量可默认 500。
- 单坐席上限可默认 100。

### 坐席负载表

展示每个启用坐席：

- 当前活跃任务数。
- 未联系数。
- 今日拨号数。
- 近 7 天处理量。
- 逾期回访数。
- 负载分。
- 建议新增数量。

### 预览与执行

预览区展示：

- 本次预计分配总数。
- 每个坐席分配数量。
- 分配涉及的学校/地区摘要。
- 风险提示和剩余未分配数量。

执行需要二次确认。确认后调用执行接口，成功后展示实际分配数量、跳过数量和批次号。

## API 设计

### 预览接口

```text
GET /api/admin/smart-assign/preview
```

查询参数：

- `school_name`: 可选。
- `region`: 可选。
- `limit`: 本次分配总量，默认 500，范围 1-5000。
- `per_agent_limit`: 单坐席新增上限，默认 100，范围 1-1000。

返回结构：

```json
{
  "pool": {
    "total_unassigned": 54150,
    "eligible": 500,
    "excluded_duplicate_phone": 120,
    "excluded_invalid_status": 30,
    "remaining_after_plan": 0
  },
  "agents": [
    {
      "agent_id": 1,
      "agent_name": "坐席A",
      "active_tasks": 80,
      "not_contacted": 60,
      "today_calls": 20,
      "handled_7d": 120,
      "overdue_follow_ups": 0,
      "load_score": 110,
      "suggested_count": 100
    }
  ],
  "plan": {
    "requested": 500,
    "planned": 500,
    "per_agent": [
      { "agent_id": 1, "agent_name": "坐席A", "count": 100 }
    ]
  },
  "warnings": []
}
```

### 执行接口

```text
POST /api/admin/smart-assign/execute
```

请求体：

```json
{
  "school_name": "测试学校",
  "region": "芗城区",
  "limit": 500,
  "per_agent_limit": 100,
  "confirm": true
}
```

执行规则：

- `confirm` 必须为 `true`。
- 服务端重新按请求参数计算候选线索和分配方案。
- 对最终选中的学生写入 `assigned_to` 和 `assigned_at`。
- 为每条分配写入操作日志。
- 写入一条批次汇总日志，包含 `batch_id`。
- 返回实际分配数量、跳过数量、每坐席分配结果和批次号。

返回结构：

```json
{
  "batch_id": "assign_20260707_150000_xxxxxx",
  "assigned_count": 500,
  "skipped_count": 0,
  "per_agent": [
    { "agent_id": 1, "agent_name": "坐席A", "count": 100 }
  ]
}
```

## 权限与审计

- 预览需要管理员身份，并且能访问线索治理或学生管理页面。
- 执行需要学生分配操作权限。
- 已停用坐席不参与推荐。
- 执行日志沿用现有分配日志和批次回滚体系。
- 批次汇总日志必须包含筛选参数、计划数量、实际分配数量和跳过数量。

## 异常处理

- 没有可分配线索：预览返回空方案，页面提示当前筛选范围无可分配线索。
- 没有启用坐席：预览不生成方案，提示先启用坐席。
- 单坐席上限太低：只分配可容纳数量，明确显示剩余未分配数量。
- 预览后数据变化：执行时重新计算，返回实际分配数量和跳过数量。
- 重复手机号：默认排除高风险重复组，页面展示排除数量并引导去线索治理处理。
- 权限不足：预览或执行返回 403，前端展示无权限状态。

## 测试范围

### 后端测试

- 预览只选择未分配、未联系、非终态线索。
- 预览排除重复手机号高风险组。
- 学校和地区筛选生效。
- 无可分配线索时返回空方案。
- 无启用坐席时返回风险提示。
- 公平分配优先补齐低负载坐席。
- 单坐席上限限制生效。
- 执行接口必须要求 `confirm=true`。
- 执行接口不信任前端学生列表，服务端重新计算。
- 执行写入学生归属、分配时间、逐条操作日志和批次汇总日志。
- 已停用坐席不参与分配。

### 前端测试

- 页面加载后展示分配池概览和坐席负载表。
- 修改学校、地区、总量、单坐席上限后刷新预览。
- 空方案、无坐席、重复手机号排除等提示正确展示。
- 确认执行时弹出二次确认。
- 执行成功后展示批次号、实际分配数量和跳过数量。
- 无权限时隐藏执行入口或展示权限提示。

### 回归测试

- 学生管理手动分配不受影响。
- 现有自动均摊不受影响。
- 学校分发不受影响。
- 分配批次回滚仍能识别智能分配批次。
- 线索治理的数据健康和重复手机号清理入口不受影响。

## 分阶段上线

### 第一阶段

- 增加后端预览和执行接口。
- 增加智能分配页面。
- 接入操作日志和批次回滚。
- 覆盖后端和前端核心测试。

### 第二阶段

- 根据真实使用调整负载权重。
- 增加“保存常用分配参数”。
- 增加学校/地区分配历史对比。

### 第三阶段

- 如果人工确认流程稳定，再评估每日自动生成建议。
- 仍不建议第一版直接自动执行分配。
