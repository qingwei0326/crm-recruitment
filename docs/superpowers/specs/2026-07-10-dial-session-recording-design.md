# 拨号会话精确记录设计

## 背景

当前系统在 `GET /api/students/phone/{student_id}` 成功时立即创建一条 `DialLog`，并把 `duration_seconds` 初始化为 0。前端只有在拨号结果弹窗完成时才调用时长接口，而且接口只更新当前坐席对该学生的最新一条拨号记录。

这造成了两个数据问题：

- 坐席返回后进入学生详情页直接更新状态，或关闭拨号结果弹窗时，业务动作已经完成，但时长请求没有发送，记录一直显示为“未记录”。
- 同一学生在短时间内重复取号会创建多条 `DialLog`，时长只更新最后一条，前面的记录保持为 0。

2026-07-10 的线上只读排查显示：当天 1527 条拨号记录中有 817 条零时长；710 次时长请求全部返回 200。邹欣辰的 322 条记录没有发送任何时长请求，但 317 条随后更新了学生状态，说明问题位于拨号会话关联和前端完成路径，不是服务器请求失败。

## 目标

- 为每次拨号建立可在前后端传递的唯一会话标识，所有后续动作精确更新同一条 `DialLog`。
- 详情页更新状态、拨号结果弹窗提交和关闭弹窗都能完成当前拨号会话。
- 防止同一未完成会话因短时间重复取号产生多条拨号记录。
- 把历史零时长记录与修复上线后真正未完成的会话分开统计。
- 保持现有客户端和接口参数兼容，不要求新旧前端同时切换。
- 第一阶段只在本地实现和验证，不部署服务器，不修改线上数据库。

## 非目标

- 不把浏览器测得的时长描述为运营商通话时长。该值仍表示从发起拨号到坐席完成记录的流程耗时。
- 不根据历史状态日志推算或回填历史通话时长。
- 不接入运营商通话详单、录音平台或外部呼叫中心。
- 不重做通话分析、坐席 KPI 或拨号频次规则。
- 不清理或删除现有 `DialLog`。

## 方案选择

采用“唯一拨号会话 ID + 生命周期状态”的方案。

没有采用仅前端补调用的方案，因为页面重载、旧缓存和重复取号仍可能造成遗漏。没有采用后端仅凭“最近一条记录”自动猜测的方案，因为同一学生存在多次拨号时可能更新错误记录。

`DialLog.id` 直接作为 `dial_log_id`，不另建会话表。现有数据模型已经具备学生、坐席、拨号时间和时长字段，增加生命周期状态即可表达本次需求。

## 数据模型

为 `dial_logs` 增加非空字符串字段 `recording_state`，合法值为：

- `pending`：新建但尚未完成的拨号会话。
- `completed`：已经成功回填流程时长。
- `legacy_missing`：修复前遗留的零时长记录，无法可靠恢复。

迁移规则：

```text
已有 duration_seconds > 0  -> completed
已有 duration_seconds <= 0 -> legacy_missing
迁移后新建 DialLog          -> pending
成功回填时长                -> completed
```

不为历史记录生成估算时长。`duration_seconds` 保持原值，`recording_state` 负责区分“历史缺失”和“当前待完成”。

应用层使用常量约束状态值，数据库列使用字符串和服务端默认值，避免 SQLite 枚举迁移带来的额外复杂度。

本仓库没有维护 Alembic 版本文件，现有增量迁移由 `app/database.py` 在启动时幂等执行。本次沿用同一模式：先检查 `dial_logs` 是否已有 `recording_state`，缺少时新增列并按上述规则回填；重复启动不得重复改表或改变已经写入的状态。迁移逻辑同时加入独立数据库迁移测试，并在本地生产数据库副本上验证后才允许进入部署阶段。

## 后端设计

### 取号接口

现有接口保持不变：

```text
GET /api/students/phone/{student_id}
```

新增可选查询参数：

```text
dial_log_id: int | null
```

响应新增字段：

```json
{
  "guardian_phone": "13800000000",
  "guardian2_phone": "",
  "dial_log_id": 12345
}
```

处理规则：

1. 如果客户端传入 `dial_log_id`，后端校验该记录属于当前坐席、当前学生且状态为 `pending`；校验通过时复用该记录，不再新增 `DialLog`。
2. 未传入 ID 时，保留现有 3 秒防重复规则；命中时返回已有记录的 ID。
3. 为兼容不能保存会话 ID 的旧客户端，再增加一个受限兜底：同一坐席、同一学生在 2 分钟内存在 `pending` 记录时复用该记录。
4. 没有可复用记录时创建 `recording_state=pending` 的新记录并返回其 ID。

两分钟兜底只用于未完成会话。已经 `completed` 的记录不会被复用，因此坐席完成一次记录后再次拨号仍会创建新会话。

### 时长接口

现有接口继续使用：

```text
PUT /api/students/dial-duration
```

参数调整为：

```text
student_id: int
duration_seconds: int
dial_log_id: int | null
```

新客户端必须传 `dial_log_id`。后端按 `dial_log_id + student_id + current_user.id` 精确查询，避免更新其他坐席、其他学生或其他会话的记录。成功后同时写入：

```text
duration_seconds = 请求值
recording_state = completed
```

未传 `dial_log_id` 时继续使用“当前坐席对该学生的最新一条记录”逻辑，以兼容旧客户端；该兼容分支也会把状态更新为 `completed`。

不存在、归属不匹配或学生不匹配的 `dial_log_id` 返回明确错误，不回退到最新记录，防止静默写错数据。

### 数据质量接口

数据质量接口保留现有总量字段，新增：

- `legacy_missing_duration`：`recording_state=legacy_missing`。
- `pending_dial_sessions`：`recording_state=pending`。
- `completed_dial_sessions`：`recording_state=completed`。

现有“未记录”兼容字段继续返回 `legacy_missing + pending`，避免旧前端报错。新前端不再把两类数据合并展示。

同一修改中修正月初时间边界：按 CST 月初转换为 UTC 后查询，避免 7 月 1 日被排除。

## 前端设计

### 共享拨号会话模块

新增一个小型共享模块管理 `sessionStorage('pendingDial')`，供移动首页、移动详情页和话务员工作台使用。模块提供：

```text
readPendingDial()
savePendingDial(session)
completePendingDial(studentId, options)
clearPendingDial(dialLogId)
```

会话结构：

```json
{
  "studentId": 42,
  "studentName": "张三",
  "dialLogId": 12345,
  "dialStartedAt": 1783650000000
}
```

`completePendingDial` 计算流程耗时，调用精确时长接口并在成功后清除对应会话。没有匹配学生或没有待完成会话时返回 no-op，不影响普通状态编辑。

存在有效 `dialStartedAt` 时，流程耗时最少记为 1 秒，避免用户快速关闭弹窗后出现 `completed + 0 秒`，并保持现有正时长统计口径。缺少开始时间的旧会话不由前端猜测时长，继续交给旧接口兼容逻辑处理。

### 发起拨号

`useDialFlow` 和 `useAgentDial` 在取号成功后读取响应中的 `dial_log_id`，再保存完整会话并跳转 `tel:`。

如果存储中已经存在当前学生的待完成会话，取号请求携带该 `dial_log_id`，后端复用同一记录。不同学生的旧会话不会被错误复用。

### 完成路径

以下路径都调用同一个 `completePendingDial`：

- 拨号结果弹窗选择状态后。
- 意向等级或回访步骤完成后。
- 移动学生详情页成功更新联系状态后。
- 话务员工作台成功更新拨号结果后。
- 用户点击结果弹窗关闭按钮或遮罩关闭时。

结果弹窗加载待处理会话时不再立即从 `sessionStorage` 删除；只有精确时长接口成功后才清除。这样组件切换、路由跳转或页面重新加载后仍可恢复会话。

状态更新属于主要业务动作，不因时长同步失败而回滚。时长同步失败时保留 `pendingDial`，显示“状态已保存，通话记录待同步”，下次进入相关页面时可以重试。

关闭弹窗不写学生状态，但会完成本次拨号会话并清除存储。按钮语义从“不记录，关闭”调整为“关闭并保留拨号记录”，避免界面文字与实际行为冲突。

### 数据质量展示

原“未记录通话”拆成两个指标：

- “历史未回填”：只读历史债务，不进入当前异常告警。
- “待完成拨号”：修复后仍处于 `pending` 的会话，需要继续关注。

已完成数量继续展示。页面说明将“通话时长”称为“拨号流程耗时”，避免暗示为运营商实际通话秒数。

### 统一统计口径

“未记录”目前不只出现在管理首页，还被通话查询、系统设置、坐席统计、坐席评分和学生时间线使用。本次必须同步调整这些入口，不能只修改一个看板：

- `admin_governance`：返回历史缺失、当前待完成和已完成三类数量。
- `admin_users` 与 `stats_agents`：坐席今日/月度指标新增 pending 与 legacy 字段。
- `operation_logs` 的通话量查询：汇总和明细返回 `recording_state`，不再只用 `duration_seconds > 0` 推导状态。
- `agent_score`：只把修复后的 `pending` 会话视为当前记录质量风险，`legacy_missing` 不进入坐席扣分信号。
- 管理移动首页、系统设置、坐席统计、坐席评分预览、通话量查询和学生时间线：统一显示“待完成”或“历史未回填”。

旧响应字段继续保留一个兼容周期，但新页面和新评分逻辑只消费明确状态字段。所有均值仍只基于大于 0 的已完成流程耗时，避免历史缺失值污染均值。

## 错误处理与安全

- `dial_log_id` 必须同时匹配当前登录用户和学生，不能仅凭主键更新。
- 管理员仍只能更新自己创建的拨号记录，保持现有 `agent_id=current_user.id` 语义。
- 精确 ID 分支失败时不自动改写最新记录。
- `duration_seconds` 保留 0 到 24 小时的现有校验。
- `sessionStorage` 不可用时继续允许拨号，并走旧接口兼容逻辑；前端记录错误但不阻塞取号。
- 时长同步失败时不丢弃待完成会话，也不重复创建新会话。

## 测试计划

### 后端

- 新建拨号记录返回 `dial_log_id` 且状态为 `pending`。
- 3 秒防重复和两分钟 pending 复用都返回同一个 ID。
- 传入合法 `dial_log_id` 时复用会话。
- 不能复用其他坐席、其他学生或已完成的会话。
- 时长接口按 ID 更新指定记录，即使同一学生存在更新的拨号记录也不写错。
- ID 归属不匹配返回错误且不修改任何记录。
- 未传 ID 的旧客户端仍能更新最新记录。
- 迁移把历史有时长和零时长记录分别标记为 `completed`、`legacy_missing`。
- 数据质量接口分别统计三种状态，并正确计算 CST 月初边界。

### 前端

- `useDialFlow` 保存后端返回的 `dialLogId`。
- 重复拨同一学生时请求携带已有 ID。
- 结果弹窗挂载时不提前清除会话。
- 选择状态、完成意向、完成回访和关闭弹窗都会按 ID 回填时长。
- 移动详情页直接更新状态后会完成匹配会话。
- 时长同步失败时状态更新保留、会话不清除，并显示待同步提示。
- 数据质量页面区分“历史未回填”和“待完成拨号”。

## 验收标准

- 每次新拨号都能获得稳定的 `dial_log_id`。
- 所有完成路径都精确更新对应拨号记录，不依赖“最新一条”猜测。
- 同一未完成拨号在两分钟内重复取号不会增加 `DialLog` 数量。
- 历史零时长记录保持原时长并显示为“历史未回填”。
- 修复后的未完成会话单独显示为“待完成拨号”。
- 现有旧客户端不因新增字段或参数失效。
- 所有验证仅在本地进行，未经再次明确确认不部署服务器。
