# 员工生命周期、学生归属与统一工作项重建设计

## 决策摘要

本次不推倒 FastAPI、React 或 SQLite 技术栈，而是重建系统中长期混用的四个领域：

- 员工在职状态与登录状态。
- 学生当前负责人和历史归属。
- 回访、家访、到校、结算等当前工作责任。
- 线索处理结果及其回收规则。

新领域模型先在服务器生产数据库的本地只读快照副本上完成迁移、回填和对账，再通过兼容投影接管现有 API。第一阶段不删除旧字段或业务表，生产环境也不在本设计实施阶段直接变更。

## 背景与审查证据

现有系统具备继续演进的基础，不需要重写整个应用：

- 后端全量测试 459 项通过，Ruff 通过。
- 前端全量测试在 8 个 worker 下 279 项通过，ESLint 和生产构建通过。
- 当前代码可在生产数据库快照副本上 1.75 秒完成现有兼容迁移，表行数、学生状态、阶段和电话均未改变。
- 迁移后 SQLite `quick_check` 为 `ok`，外键违规为 0。

问题集中在领域语义而非框架：

- `users.is_active` 同时表示临时禁用、离职和登录资格。
- `students.assigned_to` 同时承担当前工作责任、历史归属和部分报表归因。
- `FollowUp.agent_id`、`HomeVisitTask.creator_agent_id` 和 `CampusVisitTask.creator_user_id` 既被当作创建人，又被部分查询当作当前责任人。
- 当前离职接口会把非终态学生重置为未联系，并清空状态明细、意向和阶段。
- 管理员手工转移 `students.assigned_to` 后，未完成回访、家访和到校待办不会完整跟随。
- 前后端分别维护无效原因列表，规则存在漂移风险。
- 数据库结构和数据迁移集中在应用启动函数中；Alembic 已配置但没有版本文件。

2026-07-10 22:37:50 获取的生产快照审查结果：

- 数据库大小 37,425,152 字节，SHA-256 为 `cdb2162d01e5f173599b7a81ea205721b325c229ddc8629b0b7586414f907b0b`。
- 学生 57,327 名；当前未分配 48,428 名，分配给在职账号 8,899 名，没有学生挂在停用账号名下。
- 在职账号名下共有 2,034 条已经产生业务进度的非终态学生记录。

- 操作日志中有 13 次“离职用户”操作，说明同一账号可能重复执行过离职接口。

## 已确认业务规则

- 离职后账号立即失去登录资格，现有 token 立即失效。
- 离职员工名下的非终态学生不回收、不重置，进入待交接状态。
- 管理员可以在新人到岗前选择部分紧急学生转给现有话务员。
- 新员工可以一键接手交接批次中剩余的全部非终态学生。
- 学生状态、状态明细、意向、阶段、时间线和未完成待办原样继承。
- 已报名和无效学生不交给新人，继续作为原员工历史。
- 交接前的通话、备注和报名归因属于原员工；交接后的新操作属于接手员工。
- “已报名其他学校”是固定无效原因，不计本校报名，并且不可自动回收或重新分配。
- 管理员仍可在学生详情中手工纠正错误的“已报名其他学校”结果。

## 目标

- 任意时点都能准确回答学生当时归属谁、现在由谁负责。
- 创建人、历史操作人、报名归因人和当前工作责任人互不覆盖。
- 离职、部分转派和整体接手均为可审计、可重试、可回滚的事务操作。
- 所有待办使用统一状态和责任模型，避免每个业务模块自行解释人员归属。
- 无效原因由后端规则目录统一管理，前端只消费契约。
- 使用正式的版本化迁移和生产快照回归验证替代启动时临时迁移。
- 在保留旧 API 和旧字段兼容的前提下逐步切换，避免一次性大爆改。

## 非目标

- 不重写 FastAPI、React、React Query 或 SQLite 技术栈。
- 不在第一阶段迁移 PostgreSQL；新模型和事务契约需要兼容未来迁移。
- 不删除 `students.assigned_to`、现有回访、家访、到校、报名或操作日志表。
- 不在本项目中重构与归属无关的报表、系统设置、AI 分析或批量导入功能。
- 不把 `LeadsManage.jsx` 的全部拆分纳入本项目，只提取交接功能直接依赖的部分。
- 不在开发机完成迁移、对账、回滚和业务验收前修改生产数据库。

## 核心不变量

1. 每名学生最多有一条未结束的有效归属记录。
2. 兼容期内，有效归属必须与 `students.assigned_to` 一致。
3. 每条需要执行的来源记录恰好对应一个未结束工作项。
4. 历史创建人和操作人字段永不因交接而改写。
5. 只有在职员工可以成为新归属或工作项责任人。
6. 待交接学生不能进入普通未分配池或自动分配。
7. 同一个幂等键只能产生一次离职或转移结果。
8. “已报名其他学校”不能被自动回收。
9. 一个交接请求中通过冲突筛选的合格项要么完整提交，要么完整回滚；被跳过项必须明确返回。
10. 任何迁移都不得减少学生、历史操作、通话、备注或招生记录数量。

## 领域模型

### 员工当前状态 `agent_employment`

每个话务员和管理员一条当前状态记录：

- `user_id`：主键兼外键，指向 `users.id`。
- `status`：`active`、`suspended`、`handover_pending`、`offboarded`。
- `version`：乐观并发版本号。
- `status_changed_at`：最近状态变化时间。
- `offboarding_started_at`：开始离职时间，可空。
- `offboarded_at`：完成离职时间，可空。
- `updated_by`：最近执行状态变化的管理员。

语义：

- `active`：可登录、可接收新归属和工作项。
- `suspended`：临时禁用，不自动创建交接批次，当前归属保持不变。
- `handover_pending`：账号不可登录，存在未完成交接批次。
- `offboarded`：账号不可登录，已无待交接非终态学生。

兼容期由服务层同步 `users.is_active`：只有 `active` 为 `true`，其余状态为 `false`。认证层继续检查 `is_active` 和 `token_version`，直到所有调用方切换完成。

### 员工状态事件 `agent_employment_events`

状态变化追加写入，不允许更新或删除：

- `id`、`user_id`。
- `from_status`、`to_status`。
- `reason`。
- `operator_id`。
- `handover_batch_id`，可空。
- `created_at`。

该表用于审计临时禁用、恢复、开始离职和完成离职；它不替代当前状态表。

### 学生归属区间 `student_assignments`

一条记录表示一段连续归属：

- `id`、`student_id`、`agent_id`。
- `started_at`、`ended_at`。
- `start_reason`、`end_reason`。
- `started_by`、`ended_by`。
- `handover_batch_id`，可空。
- `previous_assignment_id`，可空，用于形成归属链。
- `created_at`、`updated_at`。

约束：

- SQLite 使用部分唯一索引保证同一 `student_id` 只有一条 `ended_at IS NULL` 的记录。
- PostgreSQL 迁移时使用等价的条件唯一索引。
- 所有归属变化只能调用 `assignment_service`，路由不得直接写 `students.assigned_to`。
- 新归属开始时先结束旧归属，再创建新归属，并在同一事务更新兼容字段。

已报名和无效学生在离职开始时结束当前归属区间，`students.assigned_to` 清空；历史归属仍可从本表查询，因此不需要把终态学生转给新人。

### 统一工作项 `work_items`

工作项表示“当前需要某人完成的动作”，不承担历史归因：

- `id`、`student_id`。
- `kind`：`lead_contact`、`scheduled_follow_up`、`home_visit`、`campus_visit`、`enrollment_settlement`、`help_request`。
- `status`：`open`、`blocked_suspension`、`blocked_handover`、`completed`、`cancelled`。
- `owner_agent_id`：当前责任人，可空。
- `creator_user_id`：最初创建人，创建后不可修改。
- `priority`、`due_at`、`completed_at`。
- `source_type`、`source_id`：指向现有来源记录或学生主流程。
- `handover_batch_id`，可空。
- `version`、`created_at`、`updated_at`。

约束：

- `(kind, source_type, source_id)` 唯一，避免重复回填或重复双写。
- `open` 工作项必须有在职责任人。
- `blocked_suspension` 工作项允许责任人指向暂停员工；恢复账号时重新打开。
- `blocked_handover` 工作项允许责任人指向待交接员工，但不进入员工提醒队列。
- `completed` 和 `cancelled` 工作项不可再次转移。

现有业务表继续保存业务详情：

- `FollowUp.agent_id` 保留原创建人。
- `HomeVisitTask.creator_agent_id` 保留原申请人。
- `CampusVisitTask.creator_user_id` 保留原预约人。
- `EnrollmentRecord.attributed_agent_id` 保留报名归因人。

所有“现在谁需要处理”查询改读 `work_items.owner_agent_id`。

### 交接批次 `handover_batches`

- `id`、`source_agent_id`。
- `status`：`pending`、`in_progress`、`completed`、`cancelled`。
- `version`。
- `total_items`、`remaining_items`、`transferred_items`。
- `initiated_by`、`initiated_at`。
- `completed_by`、`completed_at`，可空。
- `idempotency_key`，唯一。

每名员工同时最多有一个 `pending` 或 `in_progress` 批次。

### 交接学生 `handover_items`

- `id`、`handover_batch_id`、`student_id`。
- `source_assignment_id`。
- `status`：`pending`、`transferred`、`conflict`、`cancelled`。
- `target_agent_id`，可空。
- `transfer_id`，可空。
- `transferred_at`，可空。
- `conflict_code`、`conflict_message`，默认空。
- `created_at`、`updated_at`。

`(handover_batch_id, student_id)` 唯一。终态学生不创建交接项。

### 交接执行 `handover_transfers`

每次部分转派或整体接手一条记录：

- `id`、`handover_batch_id`、`target_agent_id`。
- `mode`：`selected` 或 `all_remaining`。
- `status`：`running`、`completed`、`failed`。
- `requested_count`、`transferred_count`、`conflict_count`。
- `operator_id`。
- `expected_batch_version`。
- `idempotency_key`，唯一。
- `created_at`、`completed_at`。

该表与 `OperationLog.batch_id` 同时写入：结构化状态供系统恢复和重试，操作日志供管理员审计页面展示。

### 处理结果目录 `lead_outcome_reasons`

- `code`：稳定代码，如 `phone_invalid`、`no_intent`、`child_declined`、`enrolled_elsewhere`、`legacy_unspecified`。
- `label`：展示文案。
- `terminal`：是否终态。
- `reclaimable`：是否允许自动回收。
- `active`：是否允许新写入。
- `sort_order`。

学生新增 `outcome_reason_code` 可空字段。兼容期继续同步 `status_detail`：

- “报好了”等确认等价的旧值映射到 `enrolled_elsewhere`。
- 166 条空白无效原因映射到 `legacy_unspecified`，不推断具体原因。
- “已报名其他学校”对应 `terminal=true`、`reclaimable=false`。
- 管理员手工纠正时允许离开该原因；批量回收接口必须拒绝该原因。

## 服务边界

### `employment_service`

- 临时禁用、恢复账号。
- 临时禁用时暂停该员工的未完成工作项，恢复时重新打开；不创建交接批次或改变学生归属。
- 开始离职和完成离职。
- 同步兼容字段 `users.is_active` 和 `token_version`。
- 写入员工状态事件。
- 禁止停用最后一个有效管理员和禁止管理员操作自己离职。

### `assignment_service`

- 创建、结束和转移学生归属。
- 同步 `students.assigned_to` 与 `students.assigned_at`。
- 维护归属链和操作日志。
- 校验目标员工在职状态。
- 为普通分配、自动分配、学校分配和交接提供同一事务入口。

### `work_item_service`

- 从学生状态和来源业务记录创建或更新工作项。
- 完成、取消、暂停和恢复工作项。
- 将学生所有未完成工作项转给新负责人。
- 保持来源表历史创建人不变。
- 统一话务员首页和管理工作中心的统计口径。

### `handover_service`

- 开始离职并创建交接批次及交接项。
- 暂停相关未完成工作项。
- 预览影响范围。
- 执行部分转派和整体接手。
- 处理幂等、版本冲突和批次完成。
- 当剩余非终态学生为 0 时完成员工离职。

### `lead_outcome_service`

- 返回前端可用的处理结果目录。
- 校验结果是否允许新写入、是否终态和是否可回收。
- 兼容旧 `status_detail` 和旧客户端负载。

路由只负责认证、请求校验和响应转换，不再直接编排跨表修改。

## 离职与交接流程

### 开始离职

同一事务中：

1. 锁定员工当前状态并校验版本。
2. 创建 `handover_batches`。
3. 查询该员工当前归属的非终态学生并创建 `handover_items`。
4. 将这些学生的未完成工作项改为 `blocked_handover`。
5. 结束已报名和无效学生的当前归属，清空兼容当前负责人。
6. 将员工状态改为 `handover_pending`。
7. 设置 `users.is_active=false` 并递增 `token_version`。
8. 写员工状态事件和批次操作日志。

学生状态、状态明细、意向、阶段、业务时间和来源记录均不改变。

### 等待交接

- 待交接学生保持原当前归属，不满足普通未分配查询条件。
- `blocked_handover` 工作项只在管理员交接中心显示，不给离职员工发送提醒。
- 管理员可按意向、逾期、地区、学校、工作项类型筛选交接项。
- 普通手工分配接口遇到待交接学生时拒绝直接修改，并引导使用交接接口。

### 部分转派

同一事务中：

1. 校验目标员工为 `active`。
2. 校验批次版本和幂等键。
3. 锁定所选 `pending` 交接项。
4. 对每名学生结束旧归属并创建目标员工的新归属。
5. 转移该学生所有 `blocked_handover` 工作项并恢复为 `open`。
6. 标记交接项为 `transferred`，写入目标员工和执行记录。
7. 更新批次计数和版本。

批次版本已经变化时，整个请求在写入前返回 HTTP 409，管理员刷新预览后重新提交。在版本校验通过后，所选项中已经不是 `pending` 的学生作为冲突项跳过，其余合格学生仍在一个事务中完成转移；响应明确返回跳过清单。若没有任何合格学生，则不写入并返回 HTTP 409。

### 整体接手

流程与部分转派相同，但选择当前批次全部 `pending` 交接项。全部成功后：

- 批次状态改为 `completed`。
- 原员工状态改为 `offboarded`。
- 写入完成事件。
- 原员工的终态历史、通话、备注和报名归因不变。

## 当前责任与历史归因

系统明确区分四种人员关系：

- 当前学生负责人：未结束的 `student_assignments`。
- 当前任务责任人：`work_items.owner_agent_id`。
- 历史操作人：通话、备注和操作日志原始人员字段。
- 报名归因人：`EnrollmentRecord.attributed_agent_id`。

报表口径：

- 当前工作量读取有效归属和未完成工作项。
- 通话量读取实际拨号人。
- 备注和跟进活动读取实际操作人。
- 报名业绩读取报名归因记录。
- 离职影响读取交接批次和交接执行记录。

任何交接都不得回写历史操作人或报名归因人。

## API 契约

### 新接口

- `GET /api/admin/handovers`：分页查询待交接、已完成和已取消批次。
- `POST /api/admin/users/{user_id}/offboarding/start`：开始离职。
- `GET /api/admin/handovers/{batch_id}`：返回批次汇总、筛选项和交接学生。
- `POST /api/admin/handovers/{batch_id}/preview-transfer`：预览部分或整体转移影响。
- `POST /api/admin/handovers/{batch_id}/transfers`：执行部分或整体转移。
- `GET /api/admin/handovers/{batch_id}/transfers`：查看执行历史和冲突。
- `GET /api/work-items`：按当前用户、队列、优先级和到期时间查询统一工作项。
- `GET /api/lead-outcome-reasons`：返回可用处理结果规则目录。

所有写接口接收：

- `idempotency_key`：客户端生成的唯一键。
- `expected_version`：员工、批次或工作项的当前版本。

版本冲突返回 HTTP 409；校验失败返回 HTTP 422；权限不足返回 HTTP 403。响应包含稳定错误代码和可展示中文消息。

### 旧接口兼容

- 现有 `/api/admin/users/{id}/offboard` 改为调用新的开始离职流程，不再重置学生。
- 兼容响应保留 `recycled_count=0`，新增 `pending_handover_count` 和 `terminal_history_count`。
- 旧学生分配 API 改为调用 `assignment_service`。
- 旧回访和招生工作中心在读取切换前继续返回原响应结构。
- 新前端只消费新交接接口；旧前端即使误调用旧离职接口，也不会再丢失进度。

## 前端设计

### 账号管理

账号状态明确显示在职、暂停、待交接和已离职，不再把所有 `is_active=false` 统一显示成离职。

`AgentManage.jsx` 仅保留账号列表、账号资料、安全操作和进入交接中心的入口。离职确认、交接预览和批次明细拆为独立组件与页面。

### 交接中心

交接中心包含：

- 待交接员工和批次汇总。
- 剩余学生、逾期回访、高意向、家访、到校和求助数量。
- 学校、地区、意向、阶段、工作项类型和逾期状态筛选。
- 勾选部分学生转给现有话务员。
- 将全部剩余学生交给新人。
- 提交前影响预览和提交后批次审计入口。
- 冲突项、失败项和可重试状态。

页面使用表格和工具栏完成高频批量操作，不使用嵌套卡片。危险操作必须展示学生数、工作项数和目标员工，并进行二次确认。

### 话务员工作台

- 待拨打、回访、家访、到校、结算和求助统一从工作项查询。
- 每条工作项显示当前责任人；详情时间线显示原创建人。
- 接手后插入“员工交接”系统时间线事件。
- 原状态、意向、阶段、截止时间和历史备注原样展示。

### 无效原因

- 前端从后端目录加载固定结果，避免桌面、移动端和拨号结果弹窗分别维护数组。
- “已报名其他学校”作为固定无效结果展示。
- 无效回收页面隐藏其批量回收选择框，并解释该原因不可自动回收。
- 管理员详情页仍允许手工纠正。

## 数据库迁移设计

### 迁移基线

当前生产库没有 `alembic_version`，Alembic 目录也没有版本文件。实施时建立明确基线：

1. 对工作副本执行已经验证的当前兼容迁移，补齐 `dial_logs.recording_state`。
2. 运行结构预检，确认所有基线表和必需列存在。
3. 基线 revision 包含从空数据库创建当前旧结构的完整操作；通过预检的现有数据库直接 stamp 到该基线，不重复建表。
4. 从基线版本开始使用 Alembic 创建新表、列、索引和回填步骤。

生产应用启动以后只检查数据库是否位于要求版本，不再执行结构重建或全表数据迁移。测试数据库仍可通过测试夹具创建，但发布数据库必须经过 Alembic。

### 本地生产快照流程

原始快照：

`backups/server-audit/crm_server_audit_20260710_223750.db`

规则：

- 原始快照保持只读，不作为应用工作库。
- 每次迁移验证从原始快照复制新的带时间戳工作库。
- `DATABASE_PATH` 只指向当前工作库。
- 工作库和迁移日志保存在 Git 忽略目录。
- 测试和日志禁止输出姓名、电话、备注正文或配置密钥。
- 只有迁移、回滚和对账全部通过后，才允许替换根目录开发库或切换本地服务路径。

正式实现前再从服务器生成一次 SQLite 在线一致性备份，重复 SHA-256 和 `quick_check` 校验，避免以过时快照做最终迁移验收。

### 回填顺序

1. 为所有用户创建 `agent_employment` 当前状态和初始事件：启用账号映射为 `active`；停用账号存在“离职用户”审计记录且没有非终态当前归属时映射为 `offboarded`；其余停用账号映射为 `suspended`，交由管理员复核。
2. 为所有 `students.assigned_to IS NOT NULL` 的学生创建有效归属记录；`started_at` 优先使用 `students.assigned_at`，缺失时使用 `students.created_at`，两者都缺失时才使用本次迁移时间，并统一标记 `start_reason=legacy_backfill`。
3. 为在职员工当前负责的非终态学生创建 `lead_contact` 工作项。
4. 为未完成回访、家访、到校、结算和求助创建对应工作项。
5. 回填处理结果目录和 `students.outcome_reason_code`。
6. 校验归属投影、来源工作项、终态和结果原因。
7. 开启新旧模型双写。

所有回填使用唯一约束保证可重复执行。回填命令重复运行时只补缺失记录，不创建重复数据。

### 当前快照预期对账

当前快照用于建立测试基准，但实现不得把数量硬编码进迁移逻辑：

## 并发、幂等与错误处理

- 每个离职和交接写请求必须携带唯一幂等键。
- 员工、交接批次和工作项使用整数版本号做乐观并发控制；批次版本不匹配时在任何写入前返回 HTTP 409。
- SQLite 写事务保持短小；读取和预览在写事务前完成，提交时重新校验版本。
- 版本通过后，已经处理的所选项作为冲突清单跳过，其他合格项继续；合格项中的任一关键写入失败则整次请求回滚。
- 没有合格项、目标员工状态变化或批次版本冲突时返回 HTTP 409，不静默覆盖。
- 重复幂等请求返回第一次成功结果。
- 目标员工在提交前变为暂停或离职时整次请求失败。
- 工作项来源缺失时将迁移或运行时错误写入结构化错误日志，不创建悬空工作项。
- 批次失败不会自动修改员工为已离职。

## 开发机与生产发布保护

开发机顺序：

1. 停止正在使用根目录数据库的本地服务。
2. 保留根目录 `crm.db` 的带时间戳备份。
3. 获取并校验最新服务器在线一致性快照。
4. 从原始快照复制迁移工作库。
5. 执行基线、升级、回填、完整性检查和领域对账。
6. 使用工作库启动本地后端并运行全量测试和 Playwright。
7. 人工验收交接中心和话务员接手流程。

生产发布不属于首轮实现，但未来必须遵守：

1. 创建新的服务器在线一致性备份并下载校验。
2. 在本地对该精确快照完成迁移演练和计时。
3. 安排维护窗口，停止写入后再次备份。
4. 部署数据库版本和兼容代码，执行迁移。
5. 运行健康检查、完整性检查和聚合对账。
6. 失败时恢复迁移前数据库和旧代码。
7. 成功后启用双写监控，不立即删除旧结构。

## 验收标准

- 离职不再重置任何非终态学生进度。
- 待交接学生不进入自动分配池，未完成工作项不再提醒离职员工。
- 管理员可以部分转派紧急学生，也可以让新人整体接手剩余学生。
- 接手后当前责任完整转移，历史操作和报名归因保持原人员。
- 已报名和无效学生不转给新人，但可按原员工查询历史。
- “已报名其他学校”在所有话务员入口可选且不可自动回收。
- 当前归属、统一工作项和兼容字段持续一致。
- 生产快照副本可从基线完整迁移，重复迁移不会重复数据。
- 所有自动测试、静态检查、构建、SQLite 完整性和数据对账通过。
- 开发机验证完成前没有任何生产数据库写入。
